# Self-Hosted Docker Deployment

One of the deployment strategies under [`self-hosted/`](../). This is the simplest path: a single docker-compose stack with postgres, the web app, and the scheduler. For other strategies see the [self-hosted index](../README.md).

## Quick Start

The fastest path is the repo-root installer, which downloads just the files this folder contains, runs setup, and tells you what to type next:

```bash
curl -fsSL https://raw.githubusercontent.com/Famick-com/FamickHomeManagement/main/install-docker.sh | bash
```

It asks two questions:
- **Install directory** (default `~/famick-home-management`)
- **TLS mode**: reverse proxy in front (default) or Kestrel inside the stack

Override either non-interactively with `FAMICK_HOME=/path/to/dir` and `FAMICK_TLS_MODE=proxy|app`. Existing files aren't overwritten; delete a file to refresh it from upstream.

Manual equivalent (if you've cloned the repo):

```bash
cd self-hosted/docker-compose
./setup.sh
docker compose up -d
```

Or use the wrapper script that runs setup + compose + waits for health:

```bash
cd self-hosted/docker-compose
./start.sh
```

The setup script generates `.env` (random DB password + JWT secret), the JWT RSA key at `data/keys/jwt-rsa.pem`, and — if app-level TLS is on — a self-signed cert at `data/certs/aspnetapp.pfx`.

## TLS modes

Two ways to terminate HTTPS:

### Reverse proxy in front (default, recommended)

Put Caddy / Traefik / nginx / Tailscale Serve between the public internet and this stack. The stack listens on HTTP only (`HTTP_PORT`, default 8088). The reverse proxy holds the real certificate (Let's Encrypt usually) and forwards plain HTTP to the container.

### Kestrel inside the stack (app-level TLS)

Kestrel terminates TLS with a self-signed cert generated by `setup.sh`. The compose overlay `docker-compose.app-tls.yml` adds the HTTPS port + Kestrel cert env vars on top of the base file. install-docker.sh writes `COMPOSE_FILE=docker-compose.yml:docker-compose.app-tls.yml` into `.env` for you, so plain `docker compose up -d` picks up both files automatically.

To switch modes later: edit (or comment / uncomment) the `COMPOSE_FILE=` line in `.env`, then `docker compose up -d`. Switching to app-TLS also needs `./setup.sh` once to generate the cert.

## Services

| Service | URL |
|---------|-----|
| Web App (HTTP) | http://localhost:8088 |
| Web App (HTTPS) | https://localhost:4431 *(app-TLS mode only)* |
| Swagger API Docs | http://localhost:8088/swagger |
| PostgreSQL | localhost:5432 |
| pgAdmin (optional) | http://localhost:5050 |

Host ports come from `HTTP_PORT` / `HTTPS_PORT` in `.env`. The defaults avoid common collisions (`88` is the macOS Kerberos KDC; `80`/`443` need root).

To include pgAdmin:

```bash
docker compose --profile tools up -d
```

## Configuration

### Environment variables

All env-var configuration is in `.env` (generated by `setup.sh` from `.env.example`).

| Variable | Description | Default |
|----------|-------------|---------|
| `HTTP_PORT` | Host port mapped to the web container's :80 | `8088` |
| `HTTPS_PORT` | Host port mapped to the web container's :443 (app-TLS mode only) | `4431` |
| `DB_PASSWORD` | PostgreSQL password | Auto-generated |
| `JWT_SECRET_KEY` | Legacy JWT signing key | Auto-generated |
| `CERT_PASSWORD` | HTTPS certificate password (app-TLS mode only) | `password` |
| `COMPOSE_FILE` | Pinned compose file list — set by installer to enable app-TLS overlay | Unset |

### Server-config overlay (`data/config/server-config.json`)

For settings beyond env vars (SMTP, public hostname, time zone, JWT issuer/audience, plugin path), the wizard and the admin "Server Settings" page write to `data/config/server-config.json`. The file is reloaded automatically by the running app when it changes. Operators can also edit it directly; use `data/config/server-config.example.json` as a template.

### Email (optional, required for password resets)

Set via the admin "Server Settings" page, or pre-seed `data/config/server-config.json` with an `EmailSettings` block. Example for Gmail SMTP:

```json
{
  "EmailSettings": {
    "Smtp": {
      "Host": "smtp.gmail.com",
      "Port": 587,
      "Username": "your-email@gmail.com",
      "Password": "your-app-password",
      "EnableSsl": true
    },
    "FromEmail": "noreply@yourdomain.com"
  }
}
```

## On-disk layout

Everything operator-mutable lives under a single `data/` folder, which docker-compose bind-mounts as `./data:/app/data`:

```text
data/
├── config/server-config.json    Server-level overlay (wizard + admin Server Settings)
├── plugins/config.json          Plugin enable/disable + API keys (admin Plugins page)
├── keys/jwt-rsa.pem             JWT signing key (generated by setup.sh)
├── certs/aspnetapp.pfx          TLS cert (only when app-TLS mode is on)
├── uploads/                     User-uploaded files (product images, etc.)
└── dataprotection/              ASP.NET Data Protection keys (cookies, antiforgery)
```

Backups: snapshot the `data/` folder plus a `pg_dump` of postgres. Both survive `docker compose down`. Both are lost on `docker compose down -v` (which deletes the postgres volume).

```bash
docker exec homemanagement-db pg_dump -U homemanagement homemanagement > backup.sql
tar -czf data-backup.tar.gz data/
```

To restore:

```bash
docker exec -i homemanagement-db psql -U homemanagement homemanagement < backup.sql
tar -xzf data-backup.tar.gz
```

## Migrating from an earlier install

Earlier installs spread state across six bind mounts (`./certs`, `./config`, `./plugins`, `./logs`, `./uploads`, `./keys`) plus a `dataprotection_keys` named volume. This release consolidates everything under one `./data/` folder. To migrate:

```bash
cd ~/famick-home-management
docker compose down

# Move existing operator data under data/ (whichever folders you have):
mkdir -p data
for d in config plugins keys uploads certs; do
    [ -d "$d" ] && mv "$d" data/
done

# Pull the new files (overwriting the old compose). The installer skips files
# that exist, so delete the old compose first if you want it refreshed.
rm docker-compose.yml setup.sh start.sh stop.sh
curl -fsSL https://raw.githubusercontent.com/Famick-com/FamickHomeManagement/main/install-docker.sh \
    | FAMICK_HOME="$PWD" bash

docker compose up -d
```

The old `dataprotection_keys` named volume is abandoned by the new compose; fresh Data Protection keys are generated under `data/dataprotection/` on first start. Effect: every signed-in user gets logged out once. Going forward, those keys persist across container restarts (fixing a latent bug — the previous mount targeted `/root/.aspnet/...` which the non-root `app` user inside the container couldn't write to, so Data Protection had been silently falling back to ephemeral keys).

Old `./logs/` is no longer mounted. The file Serilog sink has been removed; use `docker compose logs web` instead.

## Troubleshooting

### Container won't start

Check logs:

```bash
docker compose logs web
```

### Port already in use

The defaults are `HTTP_PORT=8088` and `HTTPS_PORT=4431` — chosen to avoid common collisions. If `lsof -nP -iTCP:$PORT -sTCP:LISTEN` shows something already on the port, edit `.env` and pick different values, then `docker compose up -d` again. (Port 88 is the macOS Kerberos KDC, which is why the default isn't 88.)

### `relation "X" already exists` on first start

EF Core thinks the database has zero applied migrations, but the schema is already partially there — leftover from a previous install or volume. Nuke the postgres volume and restart:

```bash
docker compose down -v
docker compose up -d
```

If `down -v` doesn't fully clear the volume (Docker Desktop on macOS occasionally retains them), use the bigger hammer:

```bash
docker compose down --remove-orphans --volumes
docker volume ls | grep famick     # confirm none remain
docker volume prune -f             # clean up orphans
docker compose up -d
```

### `password authentication failed for user "homemanagement"`

The postgres user was initialized with a different password than what's currently in `.env`. This happens when `.env` is regenerated (or the password rotated) while the postgres volume kept its old user state. Two ways out — pick one:

**Realign the postgres password to match `.env`** (fast, keeps your data):

```bash
docker compose exec postgres bash -c \
  'psql -U homemanagement -d homemanagement -c "ALTER USER homemanagement WITH PASSWORD '"'"'$POSTGRES_PASSWORD'"'"'"'
docker compose restart web
```

(The `homemanagement` user authenticates via local trust on the Unix socket inside the postgres container, so it can update its own TCP-side password without knowing the broken one.)

**Or wipe the volume and start fresh** (loses data):

```bash
docker compose down -v
docker compose up -d
```

### JWT / authentication errors

If users get 401 errors after a restart, the RSA key may be missing or corrupted:

```bash
# Verify the key exists and is valid
openssl rsa -in data/keys/jwt-rsa.pem -check -noout

# If invalid, regenerate
rm data/keys/jwt-rsa.pem
./setup.sh
docker compose restart web
```

Note: regenerating the key invalidates all existing JWT tokens. Users will need to sign in again.

### Database connection errors

Ensure PostgreSQL is healthy:

```bash
docker compose ps
docker compose logs postgres
```
